# 后训练实验方案 V2：竞赛数学 + 函数调用

> 汇报用文档 ｜ 2026-09-11
> 前序工作见 [`后训练实验报告.md`](../../后训练实验报告.md) 与 [`results/bench/WHY_BASE_WINS.md`](../bench/WHY_BASE_WINS.md)

## 摘要

第一阶段在 Qwen3-4B 上完成 SFT / GRPO 全流程验证后，发现**评测集已饱和**：4B 底座在 GSM8K 上已达 94.0%，继续训练空间很小，且三个模型分数差异无法体现训练价值。

本文提出第二阶段两个方向，均满足三个条件：**单轮任务**（不做多轮 agent）、**底座基线低**（有明确提升空间）、**答案可规则验证**（奖励信号与评测指标同构）：

1. **竞赛数学**（AIME24/25、AMC）：底座基线最低（11.7%–39.8%），同模型同方法的公开实验结果可查，是最快拿到可信提升证据的方向；
2. **函数调用**（BFCL）：基线中等（55.49%），但**直接对口智能家居落地场景**（意图 → 设备调用）。

**建议先做方向一**：它能在最短时间内验证"我们的训练管线有效"这一命题，再平移到方向二。

---

## 一、为什么要调整策略

### 1.1 第一阶段结论（已实测）

| 模型 | IFEval-lite | GSM8K |
|---|---|---|
| base（Qwen3-4B 底座） | **98.1%** | **94.0%** |
| SFT（e1 LoRA, 1 epoch） | 88.7% | 84.0% |
| GRPO（通用 RM, 250 步） | 96.2% | 95.0% |

两个问题：

1. **底座基线过高**：GSM8K 94.0%、IFEval-lite 98.1%，天花板效应明显；
2. **两次训练都没能超过底座**：SFT 明显退化（用预训练能力换取了 MiniMind 文风），GRPO 几乎没动底座（KL ≈ 0.02）。

### 1.2 三条方法论结论（直接决定 V2 的设计）

**结论一：饱和数据上训练信号会消失。**
GRPO 的组内优势信号依赖"同组回答有对有错"。当底座几乎全对时，组内奖励方差趋近于零，优势信号消失，策略不再更新——第一阶段 GRPO 的 KL 卡在 0.02、reward 仅从 −1.04 升到 −0.47，正是此现象。该现象在文献中被称为 **"too correct to learn"**（Liang et al., 2026）[¹]。

**结论二：奖励信号必须与评测目标同构。**
第一阶段用通用偏好奖励模型（InternLM2-1.8B-Reward）打分，它既不检查数学对错、也不检查约束遵循，因此对 GSM8K / IFEval **不产生有效梯度**。V2 必须改用**可验证规则奖励**（RLVR）。

**结论三：SFT 的学习率必须保守。**
第一阶段 SFT 用 lr=2e-4、全 7 个投影层、1 万条数据，loss 从 1.089 降到 0.794，属过拟合式拟合。公开的小模型智能家居工作（Home-LLM）在同类任务上用 **lr=1e-5**[⁴]。V2 的 SFT 一律压到 **1e-5 ~ 2e-5**。

**结论四：评测器本身要先验证。**
第一阶段发现并修复了自研评测器的两个判分缺陷（中文长度判分失效、结尾判分过严），修复后底座 IFEval 从 84.9% 升到 98.1%——**13 个百分点全部是判分缺陷造成的假象**。V2 在正式训练前必须先跑基线确认空间真实存在。

### 1.3 模型与模式选择

**选定：Qwen3-1.7B（非思考模式）**

| 理由 | 说明 |
|---|---|
| 基线低 | 同模型在 AIME25 上仅 11.7%（非思考）[¹] |
| 有公开对照数字 | 两个方向的实验论文都测过 Qwen3-1.7B，可直接比对 |
| 与第一阶段同代 | Qwen3 系列的 chat template 机制一致，`--no-think` 逻辑**代码零改动** |
| 本地部署可行 | 1.7B 可量化至 GGUF，满足端侧部署目标 |

> ⚠️ **一个反直觉处需实测确认**：文献中 Qwen3-1.7B 的 **思考模式**在 AIME25 达 24.9%，是非思考模式（11.7%）的两倍多[¹]。也就是说**开启思考模式会让基线翻倍、训练空间减半**。因此"关闭思考模式"不仅是为了低延迟，更是为了保住训练空间。此项在阶段 0 必须实测确认。

## 二、方向一：竞赛数学

### 2.1 为什么选它

- **底座基线最低**：这是所有规则可验证任务中，1.7B 表现最差的一类；
- **奖励与评测同构**：答案唯一且可数值比对，奖励函数就是判分函数；
- **同模型同方法已有公开结果**：可直接对照，不需要从零建立预期。

### 2.2 基线（Qwen3-1.7B，非思考模式，文献实测[¹]）

| 评测集 | 底座基线 | 训练后（GRPO） | 提升 |
|---|---|---|---|
| **AIME25** | **11.7%** | 22.8% | **+11.1** |
| **AIME24** | **12.9%** | 29.5% | **+16.6** |
| AMC | 39.8% | 59.8% | +20.0 |
| GPQA | 32.1% | 34.2% | +2.1 |
| MATH | 70.2% | 83.6% | +13.4 |

**关键判断**：该配置下 **MATH 底座已达 70.2%**，用它当评测集会重演第一阶段的饱和问题。**评测要用 AIME/AMC 这一档，训练才用 MATH。**

### 2.3 评测集

| 用途 | 数据集 | 说明 |
|---|---|---|
| **主评测** | AIME24 / AIME25 | 各 30 题，基线最低；**但题量小，必须配其它集** |
| **稳定评测** | AMC | 题量较大，用于降低评测方差 |
| **辅助评测** | [HuggingFaceH4/MATH-500](https://arxiv.org/html/2605.24140v3) | 500 题，与 MATH 训练集不相交，标准 held-out 集 |
| 对照参考 | GPQA | 观察是否损伤通用推理 |

### 2.4 训练数据

| 数据集 | 规模 | 说明 |
|---|---|---|
| **MATH 训练集** | 7.5k | 文献所用[¹]，与 MATH-500 不相交 |
| [NuminaMath-CoT](https://huggingface.co/collections/AI-MO/numinamath) | 86 万 | 备选，覆盖更广，需做污染检查 |

### 2.5 判分与奖励设计

**判分**：抽取 `\boxed{}` 内容 → 数值归一化 → 精确比对。
可复用第一阶段 `bench/gsm8k_eval.py` 的 `extract_predicted_answer` + `normalize`，改为抽取 `\boxed{}` 即可。

**奖励**（RLVR，规则计算）：

| 信号 | 分值 | 说明 |
|---|---|---|
| 答案正确 | +1.0 | 与判分函数完全一致 |
| 答案错误 | 0.0 | |
| 格式合规（含 `\boxed{}`） | +0.1 | 防止输出无法解析，保证判分可用 |
| 答案不可解析 | −0.2 | 明确惩罚，避免模型用超长输出规避判分 |

### 2.6 预期成果与风险

**预期**：AIME 提升 10 个百分点以上是可期待的（文献同模型同方法实测 +11.1 ~ +16.6）。

**风险**：

1. **AIME 仅 30 题**，单题即 3.3 个百分点，置信区间大 → **禁止只报 AIME**，必须与 AMC / MATH-500 同时汇报；
2. **数据污染**：AIME24/25 为 2024/2025 年新题，若训练集包含它们则结果失真 → 训练集须能确认为 AIME24 之前，并做抽样检查；
3. **泛化性存疑**：竞赛数学提升的是通用推理，与智能家居无直接关系（见第五节）。

## 三、方向二：函数调用

### 3.1 为什么选它

- **直接对口落地目标**：智能家居的"理解意图 → 启动设备"本质就是函数调用；
- **单轮可评测**：一次请求生成一次调用，符合"不做多轮训练"的约束；
- **规则可验证**：调用正确性可通过 AST 比对或实际执行判定，无需 LLM judge。

### 3.2 基线（Qwen3-1.7B，BFCL v4，文献实测[²]）

| 指标 | Qwen3-1.7B | Qwen3-4B（参考） |
|---|---|---|
| **Overall** | **55.49%** | 62.04% |
| Live（真实执行） | 63.48% | 75.52% |
| Non-live（AST 级） | 80.03% | 82.58% |
| **Parallel（并行调用）** | **44.44%** | 77.78% |
| **Multi-turn** | **8.38%** | 16.88% |

**读表结论**：

- **Single / Multiple 已接近饱和**（Non-live 80.03%），训练空间有限；
- **Parallel 调用是明显短板（44.44%）**，且有 33 个百分点的提升空间 —— **这是方向二的主要着力点**；
- **Multi-turn 仅 8.38%**，但按既定约束（不做多轮训练），此项**明确列为非目标**。

> 这意味着方向二的定位需要调整：**不是"整体提升函数调用能力"，而是"专攻并行调用这一短板"**。这一点必须向导师说明，因为它直接影响成果的表述方式。

### 3.3 评测集

| 用途 | 数据集 | 说明 |
|---|---|---|
| **主评测** | [BFCL v4](https://gorilla.cs.berkeley.edu/leaderboard.html) | 官方榜单，插件式评测，支持 AST 与执行两种判分 |
| 领域专项 | `acon96/Home-Assistant-Requests` test split（MIT 许可） | 智能家居实体控制，7 类设备，与训练集同源需隔离 |
| 中文专项 | `youkwan/Smart-Home-Control-Zh` | **许可与规模待核实** |

**BFCL 的分类别指标对本项目更有价值**（尤其 Parallel / Irrelevance Detection），应分子类汇报而非只报 Overall。

### 3.4 训练数据

| 数据集 | 说明 |
|---|---|
| Gorilla OpenFunctions | 文献所用[²]，40 个子领域 |
| `acon96/Home-Assistant-Requests` train split | 智能家居场景，与 test split 严格隔离 |
| 需自建 | 中文口语化请求变体（公开集为英文，**中文口语不会自动迁移**） |

### 3.5 判分与奖励设计

**判分**：AST 比对（函数名 + 参数，忽略顺序）+ 可执行性验证。

**奖励**：

| 信号 | 分值 | 说明 |
|---|---|---|
| 调用完全正确 | +1.0 | 函数名与参数全对 |
| 函数名正确、参数错 | +0.3 | 部分正确，保留梯度 |
| **调用了不存在的函数** | **−1.0** | 幻觉调用，本地部署最危险的失败模式 |
| 该拒绝却执行（Relevance Detection） | −1.0 | 安全底线 |

### 3.6 预期成果与风险

**预期**：Overall 提升空间有限（55% → 65% 量级），**主要收益应在 Parallel 子类（44.44% 起）**。

**风险**：

1. **提升幅度不如数学醒目**：Non-live 已 80%，可能只有几个百分点 → 汇报时需分子类展示，不能只报总体；
2. **评测框架成本**：BFCL 需要独立的评测环境（AST 比对 + 执行沙箱），工程量高于数学方向；
3. **中文迁移问题**：公开数据为英文，中文口语变体需自行构造，否则线上效果与评测成绩不符。

## 四、两方向对比与实施建议

| 维度 | 方向一：竞赛数学 | 方向二：函数调用 |
|---|---|---|
| 底座基线 | **11.7%**（AIME25） | 55.49%（BFCL Overall） |
| 空间最大的子项 | AIME24/25、AMC | **Parallel 44.44%** |
| 预期提升 | **+10 ~ +16 个百分点** | +5 ~ +10（主要集中在 Parallel） |
| 判分复杂度 | 低（数值比对） | 中（AST + 执行沙箱） |
| 与落地目标关系 | 弱（通用推理） | **强（直接对应智能家居）** |
| 评测噪声 | 高（AIME 仅 30 题） | 低（题量大） |
| 建议顺序 | **第一步** | 第二步 |

### 实施路线

```
阶段 0  基线确认（不训练）
        - 下载 Qwen3-1.7B，实测 AIME24/25、AMC、MATH-500 基线
        - 对照文献数字，确认空间真实存在
        - 实测思考/非思考两种模式的基线差异（决定模式选择）
        - 搭 BFCL 评测环境，跑通 1.7B 基线

阶段 1  SFT 冷启动（只教格式）
        - 目标仅是让模型学会输出 `\boxed{}` / 正确的调用格式
        - 数据 1-2k 条，lr 1e-5，1 epoch（吸取第一阶段教训）

阶段 2  RLVR（主要提升来源）
        - 奖励 = 规则判分（见 2.5 / 3.5）
        - 复用第一阶段 GRPO 管线；注意控制组内奖励方差不能为零

阶段 3  复评与部署验证
        - 全量指标复评（含分子类）
        - GGUF 量化后的准确率损失与延迟实测
```

**阶段 0 不可跳过。** 第一阶段的核心教训是：在没有确认基线空间的情况下解读了整轮数据，事后才发现评测器本身有缺陷。

## 五、需要向导师说明的限定

1. **竞赛数学与智能家居落地无直接关系**。它能最快证明"训练管线有效"，但提升的是通用推理能力，不会自动转化为设备控制能力。两条线共用同一套管线（题库 + 规则奖励 + GRPO），但定位不同。

2. **函数调用的提升幅度不会像数学那样显著**。因为 Single/Multiple 子类已接近饱和，实际收益集中在 Parallel 这一个短板上。

3. **Multi-turn 明确列为非目标**。Qwen3-1.7B 的 BFCL 多轮得分仅 8.38%，是最大短板，但按当前约束（不做多轮训练）不予处理，需在成果中明确标注此项未覆盖。

4. **所有基线数字均来自公开文献**，评测口径与我们的自研评测器不一定完全一致。**阶段 0 的首要任务就是用我们自己的口径复现这些数字**，而不是直接引用。
